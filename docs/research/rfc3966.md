# RFC 3966: The `tel` URI for Telephone Numbers

Research notes. Nothing here is a decision or a recommendation.

- Document: RFC 3966, H. Schulzrinne, December 2004, Standards Track, obsoletes RFC 2806.
- Source: <https://www.rfc-editor.org/rfc/rfc3966.txt>, read in full on 2026-10-02 (955 lines, SHA-256 `38d9aeec48d7f07120bd603f70b2da478218ffd3356eb362a651a31d0ff816bd`).
- Every statement below was read in that text. Section numbers refer to the RFC. Quoted words are the RFC's.

## 1. Purpose (section 1)

- The `tel` URI identifies a telephone number. It is "a globally unique identifier ('name') only; it does not describe the steps necessary to reach a particular number and does not imply dialling semantics."
- It distinguishes an address-of-record or identifier (what the URI carries) from a dial string (digits, symbols and pauses a user enters). "Dial strings are beyond the scope of this document."
- The dialling application knows the local context and converts the number into a dial sequence.
- The URI does not specify call type (voice, fax, data).

## 2. Syntax (section 3)

```
telephone-uri        = "tel:" telephone-subscriber
telephone-subscriber = global-number / local-number
global-number        = global-number-digits *par
local-number         = local-number-digits *par context *par
par                  = parameter / extension / isdn-subaddress
isdn-subaddress      = ";isub=" 1*uric
extension            = ";ext=" 1*phonedigit
context              = ";phone-context=" descriptor
descriptor           = domainname / global-number-digits
global-number-digits = "+" *phonedigit DIGIT *phonedigit
local-number-digits  =
   *phonedigit-hex (HEXDIG / "*" / "#")*phonedigit-hex
domainname           = *( domainlabel "." ) toplabel [ "." ]
domainlabel          = alphanum
                       / alphanum *( alphanum / "-" ) alphanum
toplabel             = ALPHA / ALPHA *( alphanum / "-" ) alphanum
parameter            = ";" pname ["=" pvalue ]
pname                = 1*( alphanum / "-" )
pvalue               = 1*paramchar
paramchar            = param-unreserved / unreserved / pct-encoded
unreserved           = alphanum / mark
mark                 = "-" / "_" / "." / "!" / "~" / "*" /
                       "'" / "(" / ")"
pct-encoded          = "%" HEXDIG HEXDIG
param-unreserved     = "[" / "]" / "/" / ":" / "&" / "+" / "$"
phonedigit           = DIGIT / [ visual-separator ]
phonedigit-hex       = HEXDIG / "*" / "#" / [ visual-separator ]
visual-separator     = "-" / "." / "(" / ")"
alphanum             = ALPHA / DIGIT
reserved             = ";" / "/" / "?" / ":" / "@" / "&" /
                       "=" / "+" / "$" / ","
uric                 = reserved / unreserved / pct-encoded
```

Consequences of the grammar, read from the rules above:

- A global number is `+` followed by digits and visual separators, with at least one digit.
- `global-number-digits` is built from `phonedigit`, which has no hex letters, `*` or `#`. Only `local-number-digits` uses `phonedigit-hex`.
- The ABNF contains no space character. A space is not in `visual-separator`, `phonedigit`, `unreserved` or `reserved`.

Other rules in section 3:

- The reserved characters `+`, `;`, `=` and `?`, when used as delimiters, MUST NOT be percent-encoded. They MUST be percent-encoded inside parameter values.
- Characters outside the "reserved" and "unsafe" sets are equivalent to their percent encoding.
- A parameter name, the ISDN subaddress, the extension and the context MUST NOT appear more than once. `isub` or `ext` comes first, then `phone-context`, then other parameters in lexicographic order.

## 3. Comparison (section 4)

Two `tel` URIs are equivalent if:

- both are local or both are global (start with `+`);
- the number digits are equal after removing all visual separators;
- `phone-context` values match (compared as a host name for a domain, digit by digit after removing separators for a global number);
- parameters match by name regardless of order, and a parameter present in only one URI makes them unequal;
- comparison is case-insensitive. Parameter names and values SHOULD be lower case.

## 4. Phone numbers (section 5.1)

- A number can be global (E.164) or local. "All phone numbers MUST use the global form unless they cannot be represented as such." Emergency numbers, some directory-assistance numbers and service codes such as "411" and N11 cannot be global and need a local number with a context.
- "Implementations MUST NOT assume that telephone numbers have a maximum, minimum, or fixed length, or that they always begin with or contain certain digits."

### Separators (5.1.1)

- Numbers MAY contain visual separators. They "merely aid readability and are not used for URI comparison or placing a call."
- "Although ITU-T E.123 recommends the use of space characters as visual separators in printed telephone numbers, 'tel' URIs MUST NOT use spaces in visual separators to avoid excessive escaping."

### Letters (5.1.2 and 5.1.3)

- 5.1.2: "The URI format does not support this notation" (alphabetic characters corresponding to keypad digits), because the mapping is "not completely uniform internationally, although there are standards [E.161][T1.703] addressing this issue."
- 5.1.3: the values A to F (BCD) and the DTMF symbols `*`, `#` and A to D "may not be included in global numbers" under E.164. "Their meaning in local numbers is not defined here, but they are not prohibited."

### Global numbers (5.1.4)

- Identified by the leading `+`. They MUST be composed of country and national number as in E.123 and E.164. They are "unambiguous everywhere in the world and SHOULD be used."

### Local numbers (5.1.5)

- Unique only within an area or network part (PBX, state, carrier, country).
- "Local numbers SHOULD NOT be used unless there is no way to represent the number as a global number."
- A local number MUST have a `phone-context` that identifies its scope. The context is either initial digits of a global number (for example `+33`) or a domain name (for example `houston.example.com`). It is not a prefix that turns the number into an E.164 number.
- A recipient that only identifies need not understand the context. A recipient that places a call MUST understand it.

## 5. Parameters (sections 5.2 to 5.4)

- `isub`: ISDN subaddress. `ext`: extension behind a non-ISDN PBX. At most one of the two may appear.
- Other parameters: mandatory ones start with `m-`. An implementation MAY ignore optional parameters and MUST NOT use a URI that contains unknown mandatory parameters. `phone-context` is mandatory; `isub` and `ext` are optional.
- Entities that forward a URI MUST NOT delete or modify optional parameters they do not understand.

## 6. Examples (section 6)

```
tel:+1-201-555-0123
tel:7042;phone-context=example.com
tel:863-1234;phone-context=+1-914-555
```

## 7. Rationale highlights (section 7)

- 7.3: the scheme is named `tel` rather than `callto`, because "URI schemes locate a resource and do not specify an action to be taken."
- 7.4: the `+` in an E.164 number indicates that an international prefix is required. It is not what the user dials: "+1-212-555-3141" is dialled as 00-1-212-555-3141 in many countries.

## 8. Use in HTML (section 8)

- Links "SHOULD enclose the telephone number so that users can easily predict the action taken when following the link".
- On a public page, the number in the URI "SHOULD always be in the global form, even if the text of the link uses some local format".
- The RFC's own example shows letters only in the link text, not in the URI: `<a href="tel:+1-555-438-3732">1-555-IETF-RFC</a>`.

## 9. SIP (section 9, informative)

Covers translation of `tel` URIs by SIP proxies and dial plans. It is not about text detection or display and was read but is not summarized here.

## 10. Security considerations (section 11)

- "Web clients and similar tools MUST NOT use the 'tel' URI to place telephone calls without the explicit consent of the user of that client."
- Risks named: calls may incur costs; the URI may be used to place malicious or annoying calls; a call takes the phone line off-hook; a call may reveal the user's number in caller identification and let an attacker correlate it with other information.
- "This is particularly important for 'tel' URIs embedded in HTML links, as a malicious party may hide the true nature of the URI in the link text." The RFC's examples have link text that differs from the target number.
- "tel" URIs may reveal private information like phone numbers as text, and "the presence of the tel: schema identifier may make it easier for an adversary using a search engine to discover these numbers."

## 11. Changes since RFC 2806 (section 12)

References to carrier selection, dial context, fax and modem URIs, post-dial strings and pause characters were removed. The syntax now conforms to RFC 2396.
